# G915 support in this fork

The G915 page provides a base color, individual key colors, overall brightness,
and G1–G5 remapping in three M-banks. Bindings use the
existing shortcut, mouse, tap/hold and macro engine. Ordinary typing keys use
Windows' normal HID input path unless regular-key overrides are enabled. Macro recording is available in the macro editor;
the physical MR key is not yet connected to recording.

Recording on Windows shows a live input count. Press RECORD, type the shortcut
(for example Ctrl+C), then STOP to put the captured steps into the macro. Device
status refreshes preserve the active recording. Software-forwarded input is
accepted; G Nexus's own tagged macro output is excluded to prevent feedback.
Regular keys can also be assigned using the optional Windows-wide mode below.

## Regular-key assignments (Windows)

Open **Regular keys**, choose a key on the layout (or select another key from
the list), and assign a key, shortcut, mouse action or macro. Enable
**regular-key overrides (Windows-wide)** and apply. These assignments use one
table across M1–M3; the G-key banks remain separate. **Restore default** removes
an override. Changes persist in `g915.json` and its usual configuration backups.

This first implementation is Windows-wide, rather than specific to the G915.
It applies to other connected keyboards too. It runs only while G Nexus is
running, the G915 is reachable, and overrides are enabled. Disconnect detection
is periodic, so deactivation can take about 2.4 seconds. It writes no driver,
registry scan-code map or keyboard firmware. G915-only suppression is not
implemented.

**Pause overrides now** and **Ctrl+Alt+Pause** stop the assignments without
deleting them. Apply again to resume. Overrides pause during macro recording,
so original keys are recorded. Remapped source presses and releases are both
consumed; keys held during an assignment change are released before the new
table takes effect. An already-held unmapped key remains native until release.
Shared output modifiers are retained until their last assignment is released.

The callback queues work to a separate playback thread. It ignores G Nexus's
tagged output, so mappings such as A→B and B→C do not recursively chain. Native
Windows hook delivery is required outside the app; the in-window macro capture
fallback is not a system-wide remapper. Elevated applications may require G
Nexus to run at the same privilege level, and software reading raw device input
can bypass user-mode remapping. Secure Windows combinations are not overridden.

Protocol-independent Windows APIs used here:
[LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc),
[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

## Per-key colors

Open **Per-key colors**, select keys on the keyboard layout, choose a color,
and click **Color selected keys**, then **Apply and save**. Selection can include
letters, modifiers, navigation keys, number pad keys, G1–G5, available media
controls and the logo. **Select WASD** and **Select all** help with groups.
**Use base color** removes the selected overrides; **Clear all individual
colors** removes every override. Disabling individual colors keeps the saved
map for later and displays the base color across the keyboard.

The worker discovers all three `0x8081` bitmap pages and exposes available key
names. Keyboard lighting IDs are not HID usages: A=1, W=23, LeftCtrl=104,
G1=180, Logo=210. Standard positions are HID usage minus three; modifiers and
special controls have separate mappings. F13–F24 are not mapped to color IDs
because that arithmetic would overlap the modifier range. The G915 has no
individual LED for the volume roller. Unsupported controls are disabled.

Per-key mode uses software lighting control (`0x8071`), static effects and
`0x8081` frames (four key/R/G/B tuples per request; function 7 commits the
frame). Every advertised LED receives either an override or the base color,
so deleted overrides and a return to base-only mode cannot leave stale paint.
No frame is committed after a failed data packet. BUSY/timeouts are retried
with a short backoff, and the first frame after claiming control is repeated.
Brightness is still controlled by the keyboard's brightness feature.

`per_key_enabled` and `key_colors` persist in `g915.json` and configuration
backups. Saved colors are reapplied on reconnect and when WirelessDeviceStatus
requests software reconfiguration after waking. The device cannot report its
current per-key colors back; the UI shows saved/draft colors, not a live read.
Your LIGHTSPEED LED bitmap has been read successfully; the visible per-key
colors still need a physical-keyboard test. USB/Bluetooth remain unverified.

When Windows' global recorder returns no keyboard events, the editor uses key
events received directly by its focused window. Keep G Nexus focused when using
this fallback. It records keyboard shortcuts only; native capture remains the
path for mouse input and actions in other applications. Native and local copies
of the same key are never combined.

G-key capture is off initially. Close G HUB, open the G915 tab, enable the
controls you want, choose assignments, and press **Apply and save**. Controls
without a feature on the active transport are disabled. Settings are stored in
`g915.json` next to the profile directory and included in whole-configuration
backups. The software restores device mode and releases all injected keys on
disconnect or exit; it never writes the keyboard's onboard profile sectors.

## Connection validation

| Connection | Current evidence |
| --- | --- |
| LIGHTSPEED | Discovery verified via receiver `046D:C541`, HID++ 4.2, device index 1. RGB zones, brightness range and battery voltage read successfully. User confirmed lighting, in-app macro capture and G-key macro playback. Regular-key assignments still need a physical-key test. |
| USB cable | Discovery probes direct index `FF` and receiver-style indices. Existing Solaar captures identify G915 USB `046D:C33E`; not yet tested locally. |
| Bluetooth | Uses a vendor HID++ long-report collection if Windows exposes one. Exact feature availability and Windows access remain unverified; ordinary Bluetooth typing alone does not imply lighting or G-key control support. |

The current page displays battery voltage, not a guessed percentage. This first
version does not include animated effects, onboard profile editing,
per-application keyboard profiles, or G915 X/TKL variants.

## Windows development

Install Rust's `stable-x86_64-pc-windows-gnu` toolchain and a GCC-based MinGW-w64
toolchain (not LLVM-only mingw). Put its `bin` directory on PATH or pass it to:

```powershell
./tools/windows-dev.ps1 -ToolchainBin 'C:\path\to\mingw64\bin' -Action Build
./tools/windows-dev.ps1 -ToolchainBin 'C:\path\to\mingw64\bin' -Action Test
./tools/windows-dev.ps1 -ToolchainBin 'C:\path\to\mingw64\bin' -Action Check
```

The default output is `%LOCALAPPDATA%\GnexusBuild`; `-TargetDir` overrides it.
The debug executable is `debug\g13-studio.exe`; keep `WebView2Loader.dll` beside it
(the build helper copies it automatically). Building does not install the app
or the headset audio effect. A non-fatal duplicate-manifest linker warning is
currently emitted by the upstream Windows GUI build.

`cargo run -p g13-daemon --bin g915-probe` checks the app's discovery and battery
reading without changing settings (use the GNU toolchain as above).
`tools/g915_probe.py` uses Python's `hidapi` package for read-only transport and
feature diagnostics. `tools/g915_ui_smoke.cjs` uses Playwright with Microsoft Edge:
serve `crates/g13-gui/ui` on `127.0.0.1:8765`, then run it with Node. The browser
mock tests UI interactions without changing any hardware settings.

`cargo run -p g13-daemon --bin recorder-probe` checks actual Windows hook delivery
using an F24 press/release. `-- --physical` instead listens for 60 seconds and
reports counts plus whether Ctrl/C arrived; no typed text is printed.
`cargo run -p g13-daemon --bin remap-probe` checks real F24→F23 suppression,
replacement delivery, restoring defaults and disabling while a key is held.

## M1–M3 profiles

M1, M2 and M3 now keep separate base colors, per-key colors, brightness, regular
key overrides and G1–G5 assignments. Macros share one library across profiles.
Existing configurations start with the previous lighting and regular mappings
in all three profiles; existing G-key banks stay intact.

Choose M1, edit colors and keys, and Apply and save. Repeat for M2 and M3.
Once saved, press a physical M-key or click its button in the app to activate
its colors and mappings together. G Nexus must be running, with G HUB closed.
USB/LIGHTSPEED must expose the G/M-key feature; Bluetooth support depends on
the capabilities reported by that connection. This writes the app configuration,
not the keyboard's onboard flash.

With unsaved edits, clicking M1–M3 selects the profile to edit. Apply and save
saves all three drafts and activates the selected one. A physical profile change
updates the active status but preserves any draft being edited. Discard changes
returns to the current active profile. Held outputs and running mapping macros
are released before a profile change.

The top row shows M1–M3, MR, LIGHTSPEED, Bluetooth, game mode, brightness and
status indicators. M-key LEDs indicate the active profile using their fixed
hardware color, not a selectable RGB color. The other top-row controls retain
their hardware roles; they are not custom assignments in this update.
